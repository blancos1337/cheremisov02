## 3. ТЕОРЕТИЧЕСКОЕ ВВЕДЕНИЕ

### 3.1. Удалённые репозитории

Удалённый репозиторий (Remote Repository) — это версия проекта, размещённая на сервере. Он позволяет разработчикам обмениваться изменениями и совместно работать над проектом.

Основные команды для работы с удалёнными репозиториями:

| Команда | Назначение |
|---|---|
| `git remote -v` | Просмотр подключённых удалённых репозиториев |
| `git remote add <name> <url>` | Добавление удалённого репозитория |
| `git remote remove <name>` | Удаление удалённого репозитория |
| `git fetch <remote>` | Получение изменений из удалённого репозитория |
| `git pull <remote> <branch>` | Получение и объединение изменений |
| `git push <remote> <branch>` | Отправка изменений на сервер |

### 3.2. Модель совместной разработки

В GitLab часто используется модель Fork & Merge Request.

Основные этапы работы:

1. Fork — создание собственной копии исходного проекта.
2. Clone — клонирование репозитория на локальный компьютер.
3. Создание отдельной ветки для разработки.
4. Внесение изменений в файлы проекта.
5. Push — отправка изменений в удалённый репозиторий.
6. Merge Request — создание запроса на объединение изменений.
7. Code Review — проверка изменений другими участниками.
8. Merge — объединение изменений с основной веткой.

### 3.3. Синхронизация форка с upstream

При работе через Fork используются два удалённых репозитория:

- `origin` — собственная копия проекта;
- `upstream` — исходный репозиторий проекта.

Для получения последних изменений из исходного репозитория используются команды:

```bash
git remote add upstream git@gitlab.com:original-owner/original-repo.git
git fetch upstream
git checkout main
git merge upstream/main
```

После объединения изменений локальную версию можно отправить в собственный удалённый репозиторий:

```bash
git push origin main
```

## 4. ПОШАГОВАЯ ИНСТРУКЦИЯ

### Часть 1. Fork, Clone и работа с несколькими remotes

**Продолжительность: 2 часа.**

### Шаг 1. Создание базового проекта

1. Войти в GitLab.
2. Создать новый проект с названием `collab-project`.
3. Выбрать видимость Public.
4. Установить параметр Initialize repository with a README.
5. Скопировать SSH-адрес проекта.
6. Открыть терминал и выполнить клонирование:

```bash
git clone git@gitlab.com:username/collab-project.git
cd collab-project
```

7. Создать файл `CONTRIBUTORS.md` со следующим содержимым:

```markdown
# Участники проекта

| Имя | Роль |
|-----|------|
| Иванов Иван | Ментор |
```

8. Добавить файл в Git:

```bash
git add CONTRIBUTORS.md
git commit -m "docs: add CONTRIBUTORS.md"
git push origin main
```

### Шаг 2. Создание Fork

1. Открыть исходный проект `collab-project` в GitLab.
2. Нажать кнопку Fork.
3. Выбрать свою учётную запись в качестве пространства назначения.
4. Дождаться завершения создания копии проекта.

### Шаг 3. Клонирование Fork

1. Открыть собственную копию проекта.
2. Скопировать SSH-адрес.
3. Выполнить команду:

```bash
git clone git@gitlab.com:username/collab-project.git
cd collab-project
```

4. Проверить подключённые удалённые репозитории:

```bash
git remote -v
```

### Шаг 4. Добавление upstream

Добавить исходный репозиторий в качестве дополнительного удалённого источника:

```bash
git remote add upstream git@gitlab.com:original-owner/collab-project.git
```

Проверить настройки:

```bash
git remote -v
```

В результате должны отображаться два удалённых репозитория: `origin` и `upstream`.

### Шаг 5. Создание ветки и добавление участника

Создать новую ветку:

```bash
git checkout -b feature/add_contributor
```

Добавить собственные данные в файл `CONTRIBUTORS.md`.

Создать файл `MY_CONTRIBUTION.md` с описанием собственного вклада в проект.

Добавить и зафиксировать изменения:

```bash
git add CONTRIBUTORS.md MY_CONTRIBUTION.md
git commit -m "docs: add self to contributors"
```

### Шаг 6. Отправка ветки

Отправить созданную ветку в собственный удалённый репозиторий:

```bash
git push origin feature/add_contributor
```

### Часть 2. Merge Requests и Code Review

**Продолжительность: 2 часа.**

### Шаг 7. Создание Merge Request

1. Открыть собственный проект в GitLab.
2. Перейти в раздел Merge Requests.
3. Нажать New merge request.
4. Выбрать исходную ветку `feature/add_contributor`.
5. Выбрать целевую ветку `main`.
6. Заполнить заголовок и описание изменений.
7. Создать Merge Request.

### Шаг 8. Проведение Code Review

Другой участник проекта должен открыть Merge Request и проверить внесённые изменения.

Примеры замечаний:

- В таблице файла `CONTRIBUTORS.md` необходимо проверить форматирование и добавить строку разделителя `|---|---|---|` для трёх колонок.
- Создание отдельного файла `MY_CONTRIBUTION.md` является хорошим решением, но информацию о вкладе можно также объединить с README.

Замечания оставляются в виде комментариев к соответствующим строкам или изменениям.

### Шаг 9. Исправление замечаний

После получения замечаний необходимо внести исправления в локальные файлы.

Например, исправить таблицу в `CONTRIBUTORS.md`.

Добавить исправления и создать новый коммит:

```bash
git add CONTRIBUTORS.md
git commit -m "fix: correct contributors table formatting"
git push origin feature/add_contributor
```

Изменения автоматически появятся в существующем Merge Request.

### Шаг 10. Объединение изменений

После завершения проверки Merge Request можно объединить с основной веткой.

В GitLab доступны следующие варианты объединения:

- **Merge commit** — объединение с созданием отдельного коммита слияния.
- **Squash commits** — объединение нескольких коммитов в один.
- **Rebase and merge** — перенос коммитов на актуальную основу и объединение без отдельного merge-коммита.

Выбрать подходящий способ и выполнить объединение.

### Шаг 11. Обновление локального репозитория и Fork

После объединения изменений необходимо обновить локальную основную ветку:

```bash
git checkout main
git fetch upstream
git merge upstream/main
git push origin main
```

## 5. ЗАЩИТА ВЕТОК (PROTECTED BRANCHES)

Для предотвращения случайного изменения или удаления важных веток в GitLab предусмотрена функция Protected Branches.

Порядок настройки:

1. Открыть настройки проекта.
2. Перейти в раздел Settings → Repository.
3. Найти раздел Protected Branches.
4. Выбрать ветку `main`.
5. Настроить разрешения:
   - Allowed to merge — Maintainers.
   - Allowed to push — No one.
6. При необходимости включить дополнительные ограничения:
   - Code Owner Approval;
   - обязательное прохождение CI/CD.

Защищённая ветка позволяет контролировать процесс внесения изменений и повышает надёжность проекта.

## 6. КОМПЛЕКСНОЕ ЗАДАНИЕ

Выполнить следующие действия:

1. Создать Fork проекта.
2. Клонировать Fork на локальный компьютер.
3. Добавить исходный репозиторий в качестве `upstream`.
4. Создать отдельную ветку `feature/calculator`.
5. Создать файл `calc.py` с функцией сложения двух чисел:

```python
def add(a, b):
    return a + b
```

6. Отправить ветку на сервер и создать Merge Request.
7. Оставить комментарий к Merge Request другого студента.
8. Исправить замечания, полученные в ходе Code Review.
9. Объединить изменения с основной веткой.
10. Синхронизировать локальный репозиторий с исходным проектом.
11. Сохранить историю изменений в файл:

```bash
git log --oneline --graph --all > history.txt
```

## 7. ЧАСТЫЕ ОШИБКИ И ИХ РЕШЕНИЯ

### Ошибка 1. Remote origin already exists

Причина: удалённый репозиторий с именем `origin` уже подключён.

Решение:

```bash
git remote -v
git remote remove origin
```

После этого можно добавить нужный удалённый репозиторий повторно.

### Ошибка 2. Push rejected (fetch first)

Причина: удалённая ветка содержит изменения, которых нет в локальной версии.

Решение:

```bash
git pull --rebase upstream main
```

После успешного обновления повторить отправку изменений.

### Ошибка 3. Permission denied (publickey)

Причина: SSH-ключ не настроен или не добавлен в учётную запись GitLab.

Решение:

```bash
ssh -T git@gitlab.com
```

Проверить наличие SSH-ключа и добавить открытый ключ в настройки учётной записи GitLab.

### Ошибка 4. Merge Request содержит конфликты

Причина: одна и та же часть файлов была изменена в нескольких ветках.

Решение:

```bash
git checkout feature/add_contributor
git fetch upstream
git merge upstream/main
```

После этого необходимо вручную разрешить конфликты, сохранить исправленные файлы, создать коммит и отправить изменения.

### Ошибка 5. Project cannot be forked

Причина: ограничения доступа или настройки исходного проекта не позволяют создавать Fork.

Решение: проверить права доступа и настройки проекта. При необходимости обратиться к владельцу проекта.
